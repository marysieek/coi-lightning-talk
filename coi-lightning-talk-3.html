Confession

Be honest. The permission prompts are annoying, so everyone bypasses them. And then the agent runs with your ~/.ssh, your .env, your gh token, your AWS creds. One prompt injection away from a bad week.

Incus

A real Linux machine
that starts in seconds.

  • root, systemd, Docker inside, install anything
  • files come out owned by you, not root
  • open source, Linux-native, no Docker Desktop
Incus gives you system containers: a full OS that behaves like a small VM but starts like a container. That's everything an agent needs, in one isolation layer. Skip the internals; the point is it's a real machine.

So I built coi

curl -fsSL .../install.sh | bash
coi build            # once, ~5 min
cd your-project
coi shell            # Claude Code, Codex, opencode, pi
  • project mounted at /workspace
  • correct file ownership, no permission hell
  • Docker + gh + build tools ready
One command per project. Build an image once, then coi shell anywhere. Claude Code by default; Codex, opencode and pi are supported too.

Built for how agents misbehave

  • your keys, env vars and git creds never enter the container
  • need a secret inside? forward it, or mint a short-lived one
  • git hooks and agent settings are read-only, so nothing planted today runs on your host tomorrow
Not generic sandboxing. Every rule is there because of something an agent actually does. It inherits your shell, so nothing from the shell crosses. It needs a GitHub token, so a host broker mints a short-lived one. It will happily rewrite a git hook or a Claude settings file that runs on your host next session, so those are read-only.

Active defense

  • reverse shell → kill
  • data exfiltration → pause
  • secret scanning, C2, DNS tunneling → nftables, kernel-level
  • everything → JSONL audit log, coi audit -f

HIGH pauses. CRITICAL kills. No human in the loop.

Isolation is table stakes. What I wanted was to know when something goes wrong, not after. Monitoring watches the container; on HIGH it freezes it, on CRITICAL it kills it. Audit log pipes into jq or your SIEM.

Network

modewhat
restrictedinternet yes, LAN + cloud metadata no (default)
allowlistonly named hosts / CIDRs, DNS pinned via /etc/hosts
opentrusted projects only
[network]
mode            = "restricted"
dns_servers     = ["192.168.1.2"]       # only my Pi-hole on :53
allowed_ports   = [80, 443]             # no SSH, no DB ports, anywhere
allowed_domains = ["github.com:443", "10.0.0.0/8:22", "svc.internal:8000-8100"]
[[network.hosts]]                       # one LAN box, one port
ip = "192.168.1.50"  hostnames = ["redmine.local"]  ports = [443]
Three modes, and then knobs that compose: pin the DNS resolver, cap egress ports globally, give each destination its own ports, and static host entries for the one internal service the agent may reach. "Internet open, LAN only redmine on 443" is four lines. All of it is trusted-scope only, so a cloned repo can't loosen it.

Day-to-day

  • --slot 2 parallel agents, same repo, separate homes
  • --resume full history + creds back
  • snapshots: checkpoint, roll back, branch experiments
  • persistent mode: keep what the agent installed
  • coi run -- npm test same sandbox, no agent
  • coi run --prompt "bump deps, run tests, open a PR" headless, cron-friendly
Slots let you run three agents on one repo without them stepping on each other. Resume brings the conversation back into a fresh container. And coi run gives you the sandbox for plain scripts — untrusted repo, use the hardened profile.

Twice it saved me

  • DSPy pulled in a compromised litellm — the one that exfiltrated SSH keys, cloud creds, shell history. Inside the container there was nothing to steal.
  • Agent installed the wrong npm package for the Rails Herb linter. Hallucinated name, real payload. Still contained.

I didn't rotate a single credential. Twice.

These are not hypotheticals. litellm 1.82.8 on PyPI was a credential stealer; DSPy pulled it in. Weeks later Claude Code confidently npm-installed a package that doesn't exist under that name for the Herb linter — but something did exist under that name. Both times: the container had no keys, no env, restricted network. Nothing to rotate. That alone paid for the project.

Profiles: a whole setup in one word

# .coi/profiles/rails-dev/config.toml
context = "CONTEXT.md"                  # your rules, injected into the agent

[container]
image        = "coi-rails"              # its own image, built from build.sh
build.script = "build.sh"
persistent   = true

[tool]
name            = "claude"
claude.model    = "claude-opus-5"
permission_mode = "bypass"

[network]
mode            = "allowlist"
allowed_domains = ["api.anthropic.com", "rubygems.org", "github.com:443"]

[ssh]     forward_agent = true          # git push, key never enters
[ports]   pool = 3                      # dev server on localhost:<port>
[[mounts]]  host = "~/.bundle"  container = "/home/code/.bundle"

[limits]  cpu.count = "4"  memory.limit = "8GiB"  runtime.max_duration = "2h"
[monitoring]  enabled = true            # pause on HIGH, kill on CRITICAL

coi shell --profile rails-dev

One profile, everything on one screen. Its own image from a build script. Which agent, which model, how autonomous. Network policy down to ports. SSH agent forwarded, published ports so the dev server shows up on localhost. Caches mounted, CPU, memory, a two-hour cap, monitoring on. A context file so the agent starts with your rules. One flag.

Profiles compose

inherits = "rust-dev"
[container]  image = "coi-rust-nightly"
  • inherit, override only the diff
  • commit them to the repo, the whole team runs the same sandbox
  • built-in hardened for repos you don't trust
They inherit, so you only write what differs. Commit them and every teammate's agent runs the same image, limits and policy. And hardened is built in: one flag for untrusted code, and a repo can't weaken it.

coipond

A software factory.
Every node is its own coi machine.

  • Rails app: idea lands in Redmine / Jira / GitHub, workflow picks it up
  • shell steps, AI steps, several agents per flow, wired on OK / fail
  • nodes are ephemeral, or persistent so an agent remembers its previous work
  • tokens minted before, expired after, whatever happens

Not open source yet. Will be, shortly. Follow me to hear when.

Once agents are sandboxed you start chaining them, and that becomes a factory. coipond is a Rails app on top of coi. An idea shows up in Redmine, Jira or a GitHub issue; a workflow picks it up. Every node is its own coi container: shell or AI, and you can mix several agents in one flow. Nodes can be ephemeral, or persistent so a coder agent keeps the context of what it did last time. Scoped tokens are minted at the start and killed at the end, on the OK path and on the fail path. It's not public yet, but I'm open-sourcing it shortly; my handle is on the last slide. Next slide is a real one.
Karafka's autonomous coding session. Trigger, then two token generators (writer and coder) and a GitHub comments setup. "Find work" reads the issues and picks something; on fail it stops the token expirer and exits. On OK: memoize state, mint the coder token, start the expirer. Then Code, then Code review, both AI nodes in their own containers. Any failure routes to the expirer; the final expirer runs at the end regardless. This runs on its own; I read the PRs in the morning.
